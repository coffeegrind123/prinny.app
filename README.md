# prinny.app

Landing page, hosted web app, and the public Matrix server directory API.

| Path | What |
|---|---|
| `/` | Landing page |
| `/app/` | The Prinny web client, deployed by CI from `coffeegrind123/cinny` |
| `/servers/` | Human-readable server browser (reads the API below) |
| `/api/servers.json` | Combined public Matrix homeserver directory, refreshed daily |

Served by GitHub Pages from `main`. `.nojekyll` is present, so paths beginning
with `_` are served normally.

## The server directory API

`GET https://prinny.app/api/servers.json`

A merged, deduplicated list of public Matrix homeservers, rebuilt daily by
[`.github/workflows/refresh-servers.yml`](.github/workflows/refresh-servers.yml).

### Why this exists

Three good public lists exist, and **none of them send an
`Access-Control-Allow-Origin` header**, so no browser-based Matrix client can
read any of them directly. Verify it yourself:

```sh
for u in https://wiki.asra.gr/en:public_servers \
         https://servers.joinmatrix.org/servers.json \
         https://www.privacydev.net/matrix_instances.csv; do
  echo "$u"; curl -sD- -o/dev/null -H 'Origin: https://example.com' "$u" | grep -i '^access-control' || echo '  (no CORS)'
done
```

GitHub Pages *does* send `access-control-allow-origin: *`, so this repo does the
fetching and merging once a day and every client — web, desktop, Android —
reads one file.

### Sources

| id | Source | Rows | Contributes |
|---|---|---|---|
| `asra` | [wiki.asra.gr](https://wiki.asra.gr/en:public_servers) | ~1100 | Broad autogenerated crawl of servers federating with asra.gr that have registration open. Software, version, last-seen. |
| `joinmatrix` | [servers.joinmatrix.org](https://servers.joinmatrix.org/servers.json) | ~47 | Small, hand-curated, by far the richest: ISP, jurisdiction, rules/privacy links, registration method, languages, IPv6. |
| `privacydev` | [privacydev.net](https://www.privacydev.net/matrix_instances.csv) | ~35 | Privacy posture: Tor friendliness, Cloudflare, email requirement, reCAPTCHA/hCaptcha. |

Field precedence when sources disagree: **asra** wins for `software` /
`version` / `last_check` (it is a daily crawl), **joinmatrix** for registration
and descriptive metadata, **privacydev** for privacy flags.

### How deduplication works

The lists key on different things, so a naive merge produces duplicates:
asra.gr and joinmatrix.org use the **Matrix ID domain** (`tchncs.de`), while
privacydev.net lists the **client host** (`matrix.tchncs.de`). Only 1 of 35
privacydev rows matches an asra name directly.

1. **Shared-domain union.** Records are merged when they share any domain that
   some source already states (`name`, `client_domain`, `server_domain`).
2. **`.well-known` confirmation.** For what remains, a row like
   `matrix.example.org` is treated as a *candidate* client host for
   `example.org`; we fetch `https://example.org/.well-known/matrix/client` and
   link the two **only if the delegation points back at exactly that host**.
   Confirmed links are recorded in the entry's `link_evidence`.

Stripping a leading `matrix.` would be wrong, and that is not a hypothetical:
`tetaneutral.net` delegates to `tetaneutral.net`, not `matrix.tetaneutral.net`,
and `envs.net` publishes no delegation at all. Anything without positive proof
is left as the source stated it.

The same pass recovers the correct mxid domain for privacydev-only rows — this
is how `matrix-client.matrix.org` is filed under `matrix.org`.

### Response shape

```jsonc
{
  "version": 1,
  "generated_at": "2026-08-11T04:17:09.123Z",
  "refresh_interval_hours": 24,
  "counts": { "total": 1149, "open_registration": 1127, "merged_from_multiple_sources": 19 },
  "sources": [
    { "id": "asra", "url": "…", "ok": true, "stale": false, "count": 1100 }
  ],
  "servers": [
    {
      "name": "dewrito.net",              // mxid domain — the part after the colon
      "client_domain": "matrix.dewrito.net",
      "software": "Synapse",
      "version": "1.157.2",
      "last_check": "2026-08-05T07:36:13.000Z",
      "registration": { "open": true, "method": "…", "link": "https://…",
                        "captcha": true, "email_required": true },
      "privacy": { "tor_friendly": true, "cloudflare": false, "similarweb_rank": 6298573 },
      "info": { "description": "…", "homepage": "…", "rules": "…",
                "isp": "Contabo (Germany)", "jurisdiction": "United States",
                "languages": ["English"], "features": [] },
      "sources": ["asra", "joinmatrix", "privacydev"],
      "aliases": ["halogen.city"]
    }
  ]
}
```

**Absent keys mean "unknown", never "false".** Empty values are pruned to keep
the file small (1.0 MB → 306 KB; ~31 KB gzipped, which is what Pages serves),
but a real `false` is always preserved. `"captcha": false` means a source
checked and found none; a missing `captcha` means nobody surveyed it. Do not
conflate them — filtering "no captcha" on absence would wrongly return the
~1075 servers nobody has looked at.

### Reliability

- **Per-source caching.** Each source's parsed output is cached in
  `.server-cache/` (committed). If an upstream is unreachable, its last good
  copy is used and the source is marked `"stale": true` in `sources`. This is
  not theoretical: privacydev.net starts refusing TCP connections after a
  handful of requests from one address.
- **Publish gate.** `scripts/validate-servers.mjs` runs before the commit step
  and fails the workflow on a gutted or malformed list — absolute floors,
  duplicate names, invalid hostnames, and a >33% one-run shrink versus the
  previously published file. The failure it exists for is a source that still
  *parses* but silently yields a fraction of its rows.

### Running it locally

```sh
node scripts/build-servers.mjs     # writes api/servers.json
node scripts/validate-servers.mjs  # gate

# Work offline, or around an upstream that is rate-limiting you:
PRINNY_SRC_PRIVACYDEV=/tmp/pd.csv node scripts/build-servers.mjs
```

No dependencies — Node 22 standard library only.

### A note on the asra.gr Postgres DSN

The asra.gr wiki page embeds a `<sql db="pgsql://…">` tag with credentials
visible in its page source. This project deliberately does not use it: the host
is an RFC1918 address on asra.gr's internal network, and using credentials
leaked by someone's own template would be unauthorised access rather than an
integration. The rendered HTML table is the published surface and carries the
same data.

## Deploying the web app

`/app/` is written by the **Publish webapp** workflow in
`coffeegrind123/cinny`, which builds a second time with `PRINNY_BASE=/app/`
(Vite bakes the public base path into every asset URL, so the root-based build
self-hosters get would 404 under a subdirectory) and pushes the result here.

Requires a `PRINNY_APP_DEPLOY_TOKEN` secret **in the cinny repo** — a PAT with
`Contents: write` on `coffeegrind123/prinny.app`. Without it the step logs a
warning and skips, so the rest of that workflow still passes.
